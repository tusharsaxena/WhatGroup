# Dependencies — Ka0s WhatGroup

Everything you need installed to build, run, test or release this addon, with install commands for
the collection's development environment: **WSL2 / Ubuntu**.

This file answers *what to install*. [`docs/testing.md`](docs/testing.md) answers *how to verify*.
Neither repeats the other.

Every entry below names the evidence for it — a file and line, an import, or a documented command.
Nothing is listed on a hunch; where something is only plausibly needed, it says so in those words.

---

## 1. Runtime (in-game) — what a player needs

**World of Warcraft (Retail). Nothing else.**

Every library this addon uses is **vendored and committed** under `libs/`, so a player installs no
separate library addon and no dependency manager.

| Need | Version | Evidence |
|---|---|---|
| World of Warcraft, Retail | Interface `120007` (Midnight 12.0.7) | `WhatGroup.toc:1` — `## Interface: 120007` |
| Ace3 (AceAddon/AceEvent/AceConsole/AceTimer/AceDB/AceGUI), LibStub, CallbackHandler-1.0, LibSharedMedia-3.0, LibKa0s | as vendored | `WhatGroup.toc:16-25` lists each `libs\…` file directly; the folders exist under `libs/` |

`WhatGroup.toc:8` declares those libraries under `## OptionalDeps:` rather than `## Dependencies:`
**deliberately** — they are optional *external* addons, and the vendored copies satisfy them either
way. There is **no** `## Dependencies:` line, so the addon has no hard external addon requirement.

`.pkgmeta:3-4` records the same thing from the packaging side: no `externals:` block, the packager
ships the repo as-is.

## 2. Development — what a contributor installs

Four things, and only the first two are strictly required to make the green gate run.

### 2.1 Lua 5.1 — **required, and the version is not negotiable**

The headless harness loads each addon file into a sandboxed environment with **`setfenv`**, which
was **removed in Lua 5.2**. "5.2 will probably work" is false, and it fails in a way that looks like
a broken test rather than a wrong interpreter.

- Evidence: `tests/_kit/loader.lua:72` and `:91` call `setfenv(chunk, makeEnv(mocks))`;
  `tests/loader.lua:91` calls `setfenv(chunk, env)`. `tests/_kit/loader.lua:89` uses **`loadstring`**,
  also 5.1-only.
- Evidence: `.luacheckrc:4` pins `std = "lua51"`, so lint and the runtime agree on the dialect.
- **LuaJIT is an acceptable substitute** — it implements the 5.1 API including `setfenv` and
  `loadstring`. It is *not* what this repo is verified with (the box these docs were written on runs
  PUC-Rio Lua 5.1.5, and `luajit` is not installed), so treat it as compatible-in-principle rather
  than as a tested configuration.

```sh
sudo apt update
sudo apt install -y lua5.1
```

Verify:

```sh
lua5.1 -v      # expect: Lua 5.1.x
```

On Ubuntu the `lua5.1` package also provides `/usr/bin/lua` pointing at 5.1, which is why the
documented commands say plain `lua`. Confirm that on your machine before trusting it:

```sh
lua -v         # must ALSO say 5.1.x — if it says 5.3/5.4, use `lua5.1` explicitly
```

### 2.2 luacheck — **required** (half the commit gate)

- Evidence: `docs/testing.md:16` — `luacheck .` is one of the two commands that MUST be green before
  every commit; `.luacheckrc` at the repo root is its config.
- Version: **any recent** release. This repo is verified with 1.2.0; nothing here depends on a
  specific version, and pinning one would be false precision.

Installed through LuaRocks, which needs a Lua development environment:

```sh
sudo apt install -y lua5.1 luarocks
sudo luarocks install luacheck
```

Verify:

```sh
luacheck --version
```

### 2.3 lizard — **optional**, for the complexity report

- Evidence: each run bundle's `complexity.txt` is generated by
  `lizard -l lua -x "./libs/*" -x "./tests/_kit/*" .`, run from the repo root (performance-§10).
- Version: **any recent** release. This repo's current report was generated with 1.23.0.
- Not needed to build, run or test the addon. Absent `lizard` means the recorded complexity output is
  a **skip**, not that the addon is broken — see [`docs/testing.md`](docs/testing.md) →
  *Automated test records — the consolidated run*.

**Ubuntu 24.04 marks its system Python `EXTERNALLY-MANAGED` (PEP 668), so `pip install lizard`
fails.** The instruction that works is `pipx`:

```sh
sudo apt install -y pipx
pipx ensurepath
pipx install lizard
```

`pipx ensurepath` adds `~/.local/bin` to your `PATH`; open a new shell (or `source ~/.bashrc`)
afterwards.

Documented alternative, if you would rather not use `pipx`:

```sh
pip3 install --user --break-system-packages lizard
```

Verify:

```sh
lizard --version
```

> `lizard` is written in Python, so installing it pulls in Python 3 as its host. That is the **only**
> reason Python appears anywhere in this file: no script, test or build step in this repo is written
> in Python. See section 3.

### 2.4 git and diff — **required for the vendor gate**

- Evidence: `docs/testing.md:178-181` runs four `diff -r` comparisons of `libs/LibKa0s` and
  `tests/_kit` against a **sibling checkout at `../LibKa0s`**; `docs/testing.md:188` uses
  `git add --renormalize .` to fix a line-ending divergence.
- Both ship with Ubuntu (`git` may need installing on a minimal image):

```sh
sudo apt install -y git diffutils
```

Verify:

```sh
git --version
diff --version
```

The vendor gate additionally needs the **LibKa0s repo checked out as a sibling directory**
(`../LibKa0s`). That is a checkout, not a package — clone it next to this repo. Without it the
vendor gate cannot run; the green gate still can.

### What is NOT a development dependency

Stated explicitly, because each of these is a reasonable guess that happens to be wrong here:

- **No Python** for anything in this repo's own code. The test harness, the runner and the `--list`
  inventory generator are all Lua (`tests/run.lua`, `tests/loader.lua`, `tests/_kit/`). Python
  arrives only as `lizard`'s host (section 2.3).
- **No Node.js, no npm.** There is no `package.json` anywhere outside `libs/`.
- **No Python scripts, no `Makefile`, no `scripts/` directory.** The repo contains no `.py` file of
  its own, no `Makefile` and no `scripts/`. There is **one** shell script:
  `tests/_kit/run-automated-tests.sh`, the vendored automated-test runner that ships whole with the
  LibKa0s test kit (`docs/testing.md:225-227`, [`docs/automated-tests/README.md`](docs/automated-tests/README.md)).
  It needs **bash**, which Ubuntu already has, and it is a convenience wrapper — it shells out to
  the same `luacheck` / `lua tests/run.lua` / `lizard` above and treats a missing tool as a `skip`,
  never a failure. Every other documented command is typed directly.
- **No CI.** There is no `.github/` directory and no workflow. `docs/testing.md:134-137` says so
  outright: the README `tests` badge is static and hand-maintained, with no GitHub Action behind it.
- **No test dependency beyond `git` and a shell.** The suites `require` nothing outside `tests/`, and
  the only shell-outs are the harness's own: `tests/_kit/framework.lua:202-206` lists a directory with
  `ls -A` (`dir /b` on cmd.exe) because the collection takes no LuaFileSystem dependency, and the
  vendored-payload gate reads the sibling checkout with `git` — `tests/_kit/vendor_sync.lua:184`
  (the `git -C <sibling> …` runner behind its `show` and `ls-tree` reads) and `:225`
  (`git cat-file --batch`). With `git` or `../LibKa0s`
  absent, `tests/test_vendor_sync.lua`'s cases report **SKIP** with the reason and the run's exit code
  stays 0; nothing else in the tree needs a subprocess.

## 3. Release / assets

**Nothing in this section is needed to build, run or test the addon.** Do not install anything here
to fix a typo.

- **Packaging** is done by the **CurseForge/WoWAce packager**, a hosted service — not a local tool.
  Evidence: `.pkgmeta` (its config) declares `package-as: WhatGroup` (`:1`) and an `ignore:` list
  (`:6-14`), and `.pkgmeta:3-4` records that there is **no `externals:` block** because every
  library is vendored.
  There is nothing to install locally for this.
- **Media** — `media/logos` and `media/screenshots` are **committed binary assets**,
  not build outputs. No image or font tooling is required, because nothing regenerates them from
  source in this repo. If a logo needs re-cutting, that happens outside the repo with whatever tool
  the author prefers; there is no committed pipeline to reproduce.
- **`lizard`** (section 2.3) is the one tool tied to the release rhythm, since the complexity report is
  regenerated at release (performance-§10). It is listed under development because that is where it
  installs from and where a contributor may want it mid-cycle.

Nothing else: no vendored binaries, no linked system libraries, no signing tooling.

## 4. Am I set up correctly?

Run these from the repo root. All three are documented in
[`docs/testing.md`](docs/testing.md), which is where their meaning and their failure modes live.

```sh
lua tests/run.lua                                        # headless suite — non-zero exit on any failure
luacheck .                                               # must report 0 warnings / 0 errors
lizard -l lua -x "./libs/*" -x "./tests/_kit/*" .        # complexity report (optional tool)
```

The vendor gate needs the sibling checkout and is documented in full at
[`docs/testing.md`](docs/testing.md) → *The vendor gate*.

## Keeping this file honest

This file is **checked at release** along with the rest of the doc set (documentation-§5, section 7). A new
tool, a new import, or a dropped dependency changes it **in the same change** — a dependency list
that is wrong is what makes a new contributor's first hour their last.

Listing a library here does **not** license fetching it at build time. Libraries are vendored and
committed; that is the rule, and this file does not soften it.
